# Build on the Pi coding-agent SDK with Skills and subagents

Noya builds on the Pi coding-agent SDK (`createAgentSession`) instead of the lower-level `AgentHarness` recommended in the earlier integration research, and does not implement its own orchestration state machine or operation-level recovery protocol. The Context Agent is a coding-agent session whose recommended workflows for writing, syncing and answering questions are expressed as Noya's own Skills; the Writer, the Chapter Reviewer and the Sync Checker run as subagents, each with its own persisted session, created and addressed through four Noya tools (`spawn_subagent`, `send_message`, `stop_subagent`, `get_subagents`). Pi ships no built-in subagent, and its example extension runs one-shot processes with `--no-session`, so Noya implements these tools itself: they are asynchronous, push completion notices to the Context Agent, accept only validated input references rather than free-form prompts, and keep one active Writer per task. Skills are guidance the model may skip; every rule that must hold, such as author-only finalization, syncing only from finalized text, and blocking new chapters while a sync is pending, is enforced in tool code. The accepted cost is that coding-agent, built on the plain `Agent`, has no operation-level recovery: after a crash Noya reopens the persisted sessions and re-sends the last unfinished instruction, which is safe because completed steps are already saved as artifacts and every write to official content is atomic and committed to a git repository in the work directory. Built-in file tools other than shells are enabled per role for the task workspace, their directories are not restricted in code for the MVP, and git is relied on to detect and roll back stray changes to official content.

## Writing-task selection increment (2026-10-05)

The writing-tasks specification supersedes the original unrestricted-directory MVP allowance for the Context role. Context file reads and searches now allow only the current task, current work's canon, and Noya workflow skills. Explicit task selection reuses the existing TaskHub and role runtime; it does not introduce another orchestrator. A small per-work sync ownership record identifies the accepted finalization event and responsible task. Finalization records distinguish a prepared chapter file from its installed replacement so recovery cannot transfer ownership before the canonical write, even for identical prose. Canon writes and their Git commits complete before that record is marked saved.
