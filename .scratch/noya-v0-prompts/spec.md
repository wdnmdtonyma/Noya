# Noya v0：系统提示词与 Skills

Status: ready-for-agent

日期：2026-09-28。执行者：架构负责人（不交给实现 agent）。依赖的工具契约见 `.scratch/noya-v0/spec.md`（下称"实现 spec"）；领域术语以 CONTEXT.md 为准；写作要求、质量门禁与检查反馈的边界以 `docs/design/writing-brief.md`、`docs/design/chapter-review.md` 为准。

## Problem Statement

实现 spec 用代码守住了"绝不能发生"的事，但 v0 能否回答两个问题，取决于代码之外的部分：

- **A. 质量链路有没有用**：取决于 Writer 能否写出好方案和好正文、正文检查员能否挑出真问题而不乱挑、Context Agent 能否把检查结果转成 Writer 能执行的修改要求。
- **B. 软流程靠不靠得住**：取决于 Context Agent 是否知道什么时候该聊、该查、该派、该停、该问作者。

这些行为只能由系统提示词（SP）和 Skills 引导。写得不好，v0 得出的结论会是"提示词没写好"，而不是"流程设计有没有用"。

## Solution

交付四份 SP（Context Agent、Writer、正文检查员、同步核对员）和三个 Skill（写一章、Context 同步、问答）。用一组固定的作者场景在真实 DeepSeek 上运行，通过审计报告和对照比较评估，每次只改一个文件后重跑，直到场景稳定通过。

分工原则：

- **SP 写"是谁、边界是什么"，Skill 写"推荐怎么做"，代码守"绝不能做"。** SP 在迭代中尽量不动，流程调整只改 Skill，便于归因。
- **提示词不重复代码已保证的规则**，只说明被拒绝时该怎么处理（例如"`save_package` 因待同步被拒时，先做 Context 同步"）。重复会占上下文，并让模型误以为它自己在负责执行这些规则。
- **不写代码无法验证、也无法观察的承诺**。每条行为要求都应能在会话记录或产物里看出是否做到。

## User Stories

### Context Agent

1. 作为作者，我想第一次打开时 Context Agent 直接和我聊想法，不要求我先填标题、类型或导入资料。
2. 作为作者，我想只问问题时它只回答、给出来源，不擅自发起写作或修改资料。
3. 作为作者，我想它区分已确定的事实、作者的计划和未知，不把它自己的建议说成已定设定。
4. 作为作者，我想它在写入设定前先复述将写入的具体内容，等我确认后再写。
5. 作为作者，我想我粘贴的文字被先辨明性质（正文、参考、设定还是写法示例），参考不直接成为剧情事实。
6. 作为作者，我想说"写下一章"时，它只把我已经接受的要求整理进 Writing Brief，废案不进去；缺少会改变本章人物、事件或结果的关键决定时，先问我。
7. 作为作者，我想 Context Pack 只含本章需要的材料，混合核心原文、相关片段、能指回依据的短结论和明确未知，而不是把全部资料塞进去。
8. 作为作者，我想它先检查 Writer 的章节方案是否符合我的意图和作品依据，有问题先改方案再写正文。
9. 作为作者，我想 Writer 生成期间我说的新想法被及时转达；要求有变化时先更新 Package，让 Writer 以最新 Brief 为准（程序会在每条消息后附上 Writer 当前绑定的 Brief）。
10. 作为作者，我想它按"追加调整"还是"推翻方向"判断继续原 Writer 还是新开 Writer，而不是按改动字数判断。
11. 作为作者，我想每份初稿都经过正文检查员检查后才交给我。
12. 作为作者，我想它先补查待核实项，再把有依据的问题连同位置、依据、修正目标交给 Writer，不把待核实项当修改指令。
13. 作为作者，我想同一问题连续两轮没修好，或问题数量不再下降时，它停下来把当前稿和问题交给我。
14. 作为作者，我想交稿时它简短说明检查结果和未采纳的编辑建议，不贴整章正文到对话里。
15. 作为作者，我想定稿后它主动做 Context 同步，只提取正文实际带来的变化，每条附原文依据。
16. 作为作者，我想有争议或需要创作决定的同步变化由我拍板。
17. 作为作者，我想它被门禁拒绝时读懂原因并采取正确行动（补确认、先同步、修格式），而不是反复重试同一个调用。
18. 作为作者，我想它不需要我理解 Subagent、Package、会话这些内部概念。

### Writer

19. 作为作者，我想 Writer 先交一份简短的章节方案：章级概述加章内事件时间线，说明事件为什么衔接、人物为什么这样选择、选择带来什么变化，不套固定场景数或转折模板。
20. 作为作者，我想 Writer 严格遵守 Brief 的要求与边界，`leave_open` 里的事不替我决定，`creative_scope` 之外不新增重要人物、能力或世界规则。
21. 作为作者，我想 Writer 只使用 Pack 中的事实，Pack 没有的设定不当作已知。
22. 作为作者，我想 Writer 返修时只改被指出的问题段落，并对照最新 Brief，而不是整章重写或凭记忆。
23. 作为作者，我想正文用具体动作、对白和环境表现人物处境，而不是用旁白宣布结果。

### 正文检查员

24. 作为作者，我想检查员按四项质量门禁逐项给出结论，不打总分。
25. 作为作者，我想明确冲突都附上原文依据；资料没记录不被当成"不存在"，而是标为待核实。
26. 作为作者，我想人物动机判断结合处境和前文，而不是只凭性格标签。
27. 作为作者，我想编辑建议定位到具体段落，并给出修改方向，不写"不够精彩"这类空话。
28. 作为作者，我想检查员不替 Writer 写替换正文。

### 同步核对员

29. 作为作者，我想核对员只判断每条变化在定稿正文里有没有依据、是否与既有资料冲突，不补充新的变化。
30. 作为作者，我想"人物志没记录"不被当成冲突依据。

### 评估者

31. 作为评估者，我想用固定场景在真实 DeepSeek 上反复运行，比较修改前后的审计指标。
32. 作为评估者，我想每次只改一份 SP 或一个 Skill，改动与观察结果记录在迭代日志里。
33. 作为评估者，我想把 SP 与 Skill 的篇幅控制在可读范围内，避免靠堆规则修问题。

## Implementation Decisions

### 交付物与格式

- 四份 SP 各为一个 Markdown 文件，由会话工厂整体作为系统提示词注入。Skill 清单由 Pi 追加在 Context Agent 的系统提示词中；SP 不重复列出 Skill。
- 三个 Skill 各为一个目录，含 `SKILL.md`（Pi 格式：frontmatter 含 `name` 与 `description`，正文为步骤）。`description` 写清触发条件，这是 Context Agent 决定是否加载的唯一依据。
- 只有 Context Agent 加载 Skills；Writer、检查员、核对员的全部指引都在 SP 中。
- 语言：提示词正文用中文；工具名、字段名、枚举值保持英文原样，与工具契约一致。
- 篇幅上限：每份 SP 不超过约 1500 汉字；每个 Skill 不超过约 1500 汉字。超出说明在用规则堆问题，应先检查是否该由代码门禁或工具返回信息解决。

### Context Agent SP

覆盖：

- 角色：与作者对话的唯一 Agent；负责讨论、查资料、整理 Brief/Pack、派发与转达、检查方案、交稿、同步。自己不写章节正文，只做纯措辞修正。
- 事实分层：已定稿正文与正式资料是事实；作者确认的未来方向是计划；其余都是未知或建议。回答时说明来源。
- 作者确认：写入设定前复述具体变更并等待作者确认；把作者原话中表示确认的片段作为 `author_confirmation`。
- 粘贴文字的辨别规则。
- 何时加载哪个 Skill（按意图：要写或改正文 → 写一章；收到定稿通知或有待同步章节 → 同步；问问题或看资料 → 问答）。
- 与作者说话的方式：简洁；不暴露内部概念；不贴整章正文；交稿时说明检查结论。
- 被门禁拒绝时：读原因，按原因行动，同一调用不原样重试。
- Subagent 通知的含义：通知只带产物 ID，需要时再读取。

### Skill：写一章

步骤与判断点：

1. 确认本章要求：只收作者已接受的目标、事件、约束、结尾；关键决定缺失时先问；非关键细节留白或放入 `creative_scope`。
2. 查资料并组织 Pack：人物当前状态、持有物与能力、相关世界规则、资料库条目、大纲位置、相关前文原文。每段写 `来源：`。
3. `save_package`；因待同步被拒则转入同步 Skill。
4. `spawn_subagent(writer)`；等通知，不轮询。
5. 检查方案：是否满足 Brief 每条要求、是否越过边界、因果是否成立、人物选择是否有依据。有问题就用 `send_message` 给出具体调整目标；没问题就回复"方案通过，写正文"。
6. 作者在生成中插话：判断是追加调整还是推翻方向。追加调整：若改变了 Brief 中的要求，先 `save_package` 保存新版本，再 `send_message` 并带上新的 `package_id` 改绑（程序自动附上最新 Brief）；只是补充说明则直接 `send_message`。推翻方向：与作者确认新方向，`save_package` 后开新 Writer（旧 Writer 自动退役）。
7. 收到初稿 → `spawn_subagent({ role: "reviewer", draft_id })`。检查员不能接收消息；对检查结果有疑问时补查或派新检查员，不与检查员交涉。
8. 处理检查结果：先补查 `needs_verification` 项（用 `query_canon`），补查后能确认的并入问题或排除，仍不能确认的记为交给作者；把 `violation` 按"位置 + 依据 + 修正目标"发给原 Writer；编辑建议可附上，但标明不阻断。
9. 新初稿 → 新检查员整章复查。
10. 停止条件：四项全部 `passed`；或同一冲突（同一门禁项、同一依据来源）连续两轮未修复；或冲突数量没有下降。停止后交稿，说明结论与遗留问题。
11. 纯措辞修正：直接 `edit` Writer 工作文件 → `save_revision` → 仍需新检查员复查。
12. 交稿后提醒作者可以 `/finalize`，或继续提意见（回到第 6 步）。

### Skill：Context 同步

1. 触发：收到定稿通知，或发现待同步章节。
2. 读定稿正文与相关既有资料。
3. 列变化：人物状态、持有物、能力、关系、认知；新出现并会反复使用的地点、组织、规则、功法和物品；大纲节点状态与关联章节；本章摘要与重要登场角色（必需）。每条附原文摘录。
4. 不列入的：仅被提及的人物；正文未确认的推测；作者对未来的计划（除非作者在对话中明确要求写入大纲）。
5. `save_sync_proposal` → `spawn_subagent(sync_checker)` → 读核对结果。
6. `supported` 的直接纳入；`unsupported` 的删除，或改正后重新提交清单；`conflict` 的向作者说明冲突双方，请作者决定。
7. `apply_sync`（需要时附作者确认）；确认待同步已清除。

### Skill：问答

1. 用 `query_canon` 搜索并读取依据；回答注明来源 ID 或章节。
2. 区分事实、计划、未知；查不到就说查不到，不补造。
3. 不派发写作、不写资料；作者表示要改设定时，复述变更并请求确认，确认后按写入规则执行。

### Writer SP

覆盖：输入的构成（Brief + Pack）及优先级（Brief 的要求与边界 > Pack 事实 > 自行发挥）；两阶段工作（先写方案并 `submit_plan`，得到"方案通过"后再写正文并 `submit_draft`）；方案格式；初稿格式（首行 `# 标题`）；`leave_open` 与 `creative_scope` 的含义；返修方法（用 `edit` 只改被指出的段落，以消息附带的最新 Brief 为准）；表达原则（具体动作、对白、器物承载处境；不以旁白宣布关系或情绪变化；不为制造刺激引入未授权的新能力或新规则）。

不写入具体文风规则：v0 没有笔法资料，也还没有经作者认可的写法结论。作者在任务中给出的写法要求通过 Brief 传达。

### 正文检查员 SP

覆盖：四项门禁的检查范围与对照依据；`passed` / `failed` / `needs_verification` 的判定；`violation` / `needs_verification` / `suggestion` 的区分；判断边界（资料未记录 ≠ 不存在；人物行为反常需结合处境；编辑建议不伪装成冲突）；位置摘录与依据摘录必须逐字复制原文；修正目标只描述要达到的效果；只做一次整章检查并用 `save_review` 提交；被拒时按原因修正后重新提交。附一个简短示例，取自 `chapter-review.md` 示例一的一条 violation。

### 同步核对员 SP

覆盖：逐条判定；三种结论的定义；`conflict` 必须指出冲突的既有资料 ID；可用 `query_canon` 核对既有资料；不新增、不改写变化；每条都要给结论；用 `save_sync_check` 提交。

### 评估场景

固定九个场景，每个场景写成作者消息脚本（允许随模型回应小幅调整措辞），在一本从零开始的书上按顺序运行：

| # | 场景 | 通过标准（审计或产物可见） |
|---|---|---|
| S1 | 从零开书：五轮左右聊出主角、一个宗门、一门功法并确认 | 写入前有复述；确认后一次写入成功；没有未经确认的写入尝试 |
| S2 | 只问答："主角现在会什么？" | 没有 spawn、没有写入；回答带来源 |
| S3 | 写第一章完整流程 | 有 Package → 方案 → 方案检查 → 初稿 → 检查员 → 按检查结果返修或通过 → 交稿；交稿前最后一版初稿有检查结果 |
| S4 | Writer 生成中插入一个追加要求 | 要求变化时先保存新 Package，再用 `send_message` 改绑并发给原 Writer；没有开新 Writer |
| S5 | 交稿后推翻关键事件的结果 | 重新保存 Package 并开新 Writer，旧 Writer 退役 |
| S6 | `/finalize` 后同步，其中一处变化需要作者决定 | 自动开始同步；清单含摘要与重要登场角色；有争议项询问作者；同步后待同步清除 |
| S7 | 定稿后、同步前要求"写下一章" | 被拒后转入同步，而不是反复重试或绕过 |
| S8 | 粘贴一段参考小说片段，说"参考这个感觉" | 不把片段中的人物或事件写入正式资料；Brief 中作为写法要求而非事实 |
| S9 | 交稿后要求改一个词 | Context Agent 直接修改 + `save_revision` + 复查，不开新 Writer |

S3–S6 在同一本书上连续跑至少三章。每章运行 `/compare` 并记录选择。

### 指标与迭代

- 流程指标（来自审计）：场景通过率；跳过方案检查或正文检查的次数；门禁拒绝次数（按原因分类）及拒绝后是否正确处理；同一调用原样重试的次数。
- 质量指标：对照比较中最终稿胜出的比例与理由；检查员的 `violation` 经作者复核属实的比例（抽查）；每章返修轮数。
- 成本指标：每章各角色 token 与耗时。
- 迭代规则：每次只改一个文件；每次修改记录"观察到的问题 → 改了哪里 → 重跑结果"到迭代日志；同一场景至少跑两次再下结论；如果问题的根因是工具契约或门禁，就记录下来，反馈给实现 spec，而不是在提示词里打补丁。

## Testing Decisions

- 不做自动化测试。提示词的效果只能在真实模型上观察，faux 模型验证不了。
- 评估依据是审计报告、产物文件和对照比较记录，不依据模型的自我评价。
- 实现 spec 的自动化测试只保证 SP 与 Skills 被正确注入、Skill 清单出现在 Context Agent 的系统提示词中；不断言提示词内容。
- 对照比较采用固定输入、隐藏标签、由作者判断的做法；不使用模型自评分。

## Out of Scope

- 笔法资料与全书写法规则。
- 伏线相关的检查与同步。
- DeepSeek 以外模型上的调优。
- 为弥补代码门禁缺失而写的提示词规则：发现后记为实现 spec 的问题。
- 作者界面文案之外的产品文案。
