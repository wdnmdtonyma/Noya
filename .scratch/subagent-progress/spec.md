# 查看 Agent 执行过程：成果优先的信息流

Status: ready-for-agent

日期：2026-10-06。产品依据为 `docs/prd/subagent-progress/prd.md` 与同目录可离线原型 `prototype.html`（固定样例，只验证交互，不作为实现证据）。本规格把它们转成实现边界。界面上 Context Agent 显示为 "Main"，Writing Agent、正文检查员、同步核对员等子 Agent 统称 "Sub"；下文沿用领域词汇，界面文案按 PRD。

## Problem Statement

作者把写作要求交给 Context Agent 后，Context Agent 会派出 Writing Agent、正文检查员等 Sub 去完成工作。作者最关心三件事：现在在干什么、做出了什么、接下来要自己决定什么。现在的任务页只显示 Context Agent 的文字回复和一句改写过的动作提示（"Context Agent 正在查阅写作材料"）：

- 工具调用、思考、返回和错误都看不到，出问题时无从判断卡在哪里。
- Sub 只有身份、状态和"已保存 N 份工作记录"这样的概括；它被要求做什么、做到哪一步、交回了什么，都看不到。
- 稿件和检查结论散落在交稿通知里，和产生它的那次派发没有关联，作者要自己拼凑"哪一版是谁按什么要求写的"。
- 历史轮次全部平铺，越往后越难找到当前进展和需要自己决定的事。

## Solution

把任务页的信息流做成作者协作的主入口，按"作者每次发言 → Context Agent 这一轮处理"组织，成果优先：

- 进行中的一轮完整展开。Context Agent 的文字直接可见；思考与工具操作折叠成"动作 + 对象"的一句摘要。底部有一行带用时的"正在处理"。
- 结束的一轮收成"已处理 X 秒"，只留子任务卡片和 Context Agent 的最后一条回复，可以再展开。
- Context Agent 每派发或继续一个 Sub，就在对应位置出现一张子任务卡片：
  - 标题是 Context Agent 派发时写的一句任务说明；
  - 进行中时显示当前动作；
  - 结束后挂上这次交回的成果，可直接阅读。
- 点卡片，或点输入框上方的子任务入口并在列表中选择，会在右侧打开该 Sub 的详情面板（窄屏全屏）。面板按时间展示 Context Agent 的要求、Sub 的完整过程和交回的成果。
- Context Agent 和各 Sub 的过程使用同一套展示规则：保留原工具名、参数、输出和错误，不按业务角色改写。
- 执行中输入框为空时，发送键变为停止；失败、停止、中断、断线、重启都如实说明，不补造内容。

## User Stories

### 发起与跟进

1. 作为作者，我想发出要求后立刻在信息流底部看到"正在处理"和已用时长，以便知道 Context Agent 已经开始工作。
2. 作为作者，我想直接读到 Context Agent 的文字回复并看着它流式更新，以便不必展开任何东西就能跟上对话。
3. 作为作者，我想把连续的思考与工具操作收成一句"读取了 chapter-1.md，查阅了设定：万舟"这样的摘要，以便不被技术细节淹没。
4. 作为作者，我想摘要里不出现步数或调用次数，以便注意力放在做了什么，而不是做了多少。
5. 作为作者，我想动作多于三项时看到前两项加"等 N 项"，以便摘要保持一行可读。
6. 作为作者，我想正在执行的动作写成"正在修改 chapter-1.md"并排在摘要末尾，以便知道此刻卡在哪一步。
7. 作为作者，我想没成功的动作写成"修改 chapter-1.md 失败""已停止""未完成"并排在最前，以便不会把失败误读成已完成。
8. 作为作者，我想工具返回"没有改动"时看到"未改动 chapter-1.md"，以便知道文件其实没变。
9. 作为作者，我想不认识的工具直接显示原工具名，以便新工具出现时也不会被隐藏或误译。
10. 作为作者，我想展开摘要后按顺序逐行看到每个思考与工具操作，以便追查具体经过。
11. 作为作者，我想展开某一行查看原工具名、完整参数、执行中输出、最终返回和错误，以便核对 Agent 到底做了什么。
12. 作为作者，我想常规的开始和结束不单独占一行，而停止、定稿等非常规事件在原位置保留一行，以便信息流只留有意义的变化。
13. 作为作者，我想执行中输入框为空时发送键变为停止，以便一个位置就能停下工作。
14. 作为作者，我想一开始输入文字，停止键就变回发送，以便执行中也能补充要求。
15. 作为作者，我想执行中发出的补充要求交给 Context Agent 在当前执行中处理，以便不必先停止再重来。
16. 作为作者，我想另一条任务正在执行时，本任务仍能输入但暂不能发送，并看到是哪条任务在执行，以便知道为什么发不出去。
17. 作为作者，我想新任务显示空态和提示语、且不显示子任务入口，以便第一次使用时知道从哪里开始。
18. 作为作者，我想执行中任务标题下不再重复"执行中"，以便同一状态不会在页面上说两遍。

### 成果透出

19. 作为作者，我想 Context Agent 每派发一个 Sub，信息流对应位置就出现一张子任务卡片，以便知道工作交给了谁。
20. 作为作者，我想卡片标题是 Context Agent 派发时写的一句任务说明（最多两行），以便一眼知道它被要求做什么。
21. 作为作者，我想卡片上次要地显示 Sub 身份（如 writer-1），以便区分同类的多个 Sub。
22. 作为作者，我想 Context Agent 给同一个 Sub 追加要求时，卡片标为"追加要求 · writer-1"，以便区分新任务和继续修改。
23. 作为作者，我想卡片状态在全页统一使用"进行中、正在停止、已交回、已回复、未交回成果、失败、已停止、已中断"，以便同一个词在哪里都是同一个意思。
24. 作为作者，我想进行中的卡片显示 Sub 的当前动作，以便不打开详情也知道进展。
25. 作为作者，我想 Sub 交回的每份成果单独一行，带标题和一句说明，并能直接阅读，以便不钻进详情也能拿到产物。
26. 作为作者，我想检查报告的说明行直接写结论（如"通过：万舟只观察变化"），以便不打开报告就知道结果。
27. 作为作者，我想 Sub 没保存成果但给了答复时，卡片显示"已回复"和它的最后一句话，以便答复不被伪装成交付。
28. 作为作者，我想 Sub 既没有成果也没有答复时，卡片显示"未交回成果"，以便知道这次执行没有产出。
29. 作为作者，我想失败的卡片显示错误原文第一行，以便不打开详情就知道原因。
30. 作为作者，我想停止或中断的卡片说明"未收到最终返回"，以便不误以为它已完成。
31. 作为作者，我想卡片右上角常驻"过程 ›"，以便知道整张卡片可以点开看详情。
32. 作为作者，我想同一个 Sub 的每次派发或追加要求各有一张卡片、只挂那一次的成果，以便较早的版本仍能从原卡片打开。
33. 作为作者，我想结束的一轮收成"已处理 X 秒"（超过一分钟写"X 分 Y 秒"），以便回看时先看到结果。
34. 作为作者，我想收起后仍能看到子任务卡片、Context Agent 的最后一条回复和非常规事件，以便收起不丢掉重要信息。
35. 作为作者，我想点击收起行展开整轮记录、再点收起，且刷新后保留我的选择，以便按需追溯。
36. 作为作者，我想以失败、中断或停止结束的一轮收为"处理 X 秒后失败／中断／停止"并带相应颜色，且不保留出事前的最后一条回复，以便不会读成仍在进行。
37. 作为作者，我想每轮结束时 Context Agent 用一条回复说明本轮结果和需要我决定的事，以便知道下一步该做什么。
38. 作为作者，我想从卡片打开的成果在右侧只读显示，关闭后回到信息流原位置，以便读完接着看。
39. 作为作者，我想在成果页点"对这版提意见"后回到输入框，输入框上方标明针对哪份成果的哪一版并可以取消，以便意见不发错对象。
40. 作为作者，我想在成果页点"将这版定稿"并确认后，这份成果在所有位置标为"作者已定稿"，信息流留一行记录，以便定稿有明确痕迹。
41. 作为作者，我想任务执行中不能定稿，以便不会定稿到一个还在被修改的版本。
42. 作为作者，我想成果保存、检查通过、作者定稿、资料变更应用分别表达，以便查看行为不会被当成我的决定。

### 子任务详情

43. 作为作者，我想输入框上方有一个不随信息流滚动的子任务入口，以便随时找到所有 Sub。
44. 作为作者，我想进行中 Sub 的卡片还在屏幕上时，入口只显示"子任务"和总数，以便同一状态不重复。
45. 作为作者，我想卡片滚出屏幕后，只有一个 Sub 进行中时入口直接显示"writer-2 正在修改 chapter-1.md"，以便不用滚回去也知道进展。
46. 作为作者，我想多个 Sub 进行中时入口显示"N 个子任务进行中"，有失败时追加"· N 个失败"，以便失败不被进行中掩盖。
47. 作为作者，我想没有进行中但有失败时入口显示"N 个子任务失败"，都结束后显示"子任务"和总数，以便入口始终如实。
48. 作为作者，我想点击入口在输入框上方展开子任务列表，不遮罩页面，再点击、点关闭、按 Escape 或点外部都能收起，以便列表不打断我的输入。
49. 作为作者，我想列表每行显示首次派发的任务说明、身份、追加要求次数、当前动作或交回结果和状态，以便在列表中就能比较各个 Sub。
50. 作为作者，我想列表中进行中的排在前面、其余按最近活动排序、全部列出并在列表内滚动，以便最相关的在最上面。
51. 作为作者，我想从卡片或列表打开的是同一个详情面板，以便两条路径看到一致的内容。
52. 作为作者，我想宽屏时详情在右侧打开、主信息流留在左侧继续可读可输入，以便边看 Sub 边和 Context Agent 交流。
53. 作为作者，我想窄屏时详情全屏打开并可关闭返回，以便手机上也能读全。
54. 作为作者，我想右侧同一时间只显示一项，从信息流打开另一个 Sub 或成果时替换当前内容，以便不会层层叠叠。
55. 作为作者，我想详情顶部显示任务说明、身份和状态，右上角可关闭，按 Escape 也能关闭，关闭后焦点回到对应卡片，以便键盘操作连贯。
56. 作为作者，我想详情按时间展示"Context Agent 派发的要求全文 → 这次执行的过程与成果 → 追加的要求 → 下一次执行"，追加的要求出现在实际发生的位置，以便看清因果。
57. 作为作者，我想某次执行失败时末尾直接写出"执行失败："和错误原文第一行，停止或中断时写明"未收到最终返回"，以便不用逐条展开找原因。
58. 作为作者，我想每段要求旁有"原始调用"，展开可看派发调用的原工具名、完整参数和返回，以便核对 Context Agent 实际发出了什么。
59. 作为作者，我想 Sub 的过程与 Context Agent 使用同一套规则，以便不需要学两套读法。
60. 作为作者，我想 Sub 进行中时详情底部显示"正在处理"和这次执行的用时，以便知道它还活着。

62. 作为作者，我想打开详情时输入框提示"回复 Main（writer-1 不会直接收到）"，以便知道我的话发给谁。

63. 作为作者，我想任务 A 执行时查看任务 B，A 的晚到内容只更新 A，以便 B 的信息流、详情、阅读位置和输入不被打乱。

66. 作为作者，我想停止始终指向实际执行的任务，以便不会因为正在查看别的任务而停错。
67. 作为作者，我想请求停止后实时状态、进行中的卡片和输入框提示都改为"正在停止"，结束后留一行"已停止"，以便知道停止生效的过程。

69. 作为作者，我想执行已停止或中断、但工具还没收到最终返回时，该调用显示"已停止／已中断，未收到最终返回"并保留参数和已有输出，以便不出现永远转圈或伪造返回。
70. 作为作者，我想失败、停止或中断后输入区出现"继续任务"，以便明确由我决定是否继续。

73. 作为作者，我想重连后补齐遗漏内容、同一消息和调用不重复，并保留打开的详情和展开状态，以便断线对我透明。
74. 作为作者，我想程序重启后原先未结束的执行显示中断，已结束的结论和成果保留，以便明确继续前知道真实状态。
75. 作为作者，我想旧任务没保存完整过程时看到已有内容和缺失范围说明，以便不被补造的记录误导。
76. 作为作者，我想单份成果无法读取时原位置保留标题并标"暂时无法读取"，可以重试，其他记录照常可读，以便一处损坏不拖垮整页。
77. 作为作者，我想思考内容不可读时只显示"思考 · 内容不可读"，以便不被补写的内容误导。
78. 作为作者，我想不认识的内容类型保留存在与归属并可展开原文，以便新类型不会被静默丢弃。
79. 作为作者，我想 Context Agent 与多个 Sub 并行时，主信息流只有 Context Agent 的记录和子任务卡片，以便不同 Agent 的过程不混排。
80. 作为作者，我想阅读旧内容时有新回复出现"查看最新"提示，我自己滚到底后提示自动消失，以便提示不残留。
81. 作为作者，我想窄屏下卡片、列表和输入区都没有横向溢出，以便手机上也能正常使用。

## Implementation Decisions

### 1. 过程记录：从已保存会话读取，不另建事件存储

- Context Agent 和每个 Sub 已经有各自的 Pi 会话文件，记录了文字、可读思考、工具调用（名称与参数）和工具返回。过程视图从这些会话读取并归一化，不新增一份平行的事件日志，也不改作品正式内容 schema。
- 归一化后的过程项是通用的，不按业务角色分类：
  - 消息：作者或 Agent 的文字；
  - 思考：可读文字，或"不可读"标记，redacted 内容不当作文字；
  - 工具调用：调用身份、原工具名、完整参数、最终返回、错误标记和状态；
  - 系统事件：停止、定稿、中断、恢复等；
  - 未知内容：保留类型、归属与能读取的原内容。
- 读取现有消息的位置只提取 text，并过滤掉页面注入的作者提示。这一过滤规则保留，扩展为同时产出工具调用与思考，不改变已有的作者／助手消息身份和顺序。
- 执行中尚未写入会话的增量（流式文字、工具中间输出、当前动作）由本机应用订阅各 Agent 会话事件，保存在内存中，与已保存记录按消息或调用身份合并，不重复、不遗漏。现在只订阅 Context Agent，要扩展到每个活跃的 Sub 会话。
- 工具调用的状态只依据实际事件：有返回为成功或错误；所在执行已停止或中断而没有返回时，标为"已停止／已中断，未收到最终返回"，不补造返回。重启后由现有的中断标记逻辑统一处理。

### 2. 派发与执行的关联

- Sub 登记里已经按执行次数记录了开始、结束时间、本次保存的成果列表、结果（completed / stopped / failed / retired）和说明。卡片和详情的"一次执行"直接对应这里的一条记录。
- Context Agent 会话里的每次派发 Sub 或给 Writer 发消息的工具调用，各对应该 Sub 的下一条执行记录，按发生顺序配对。配对失败（旧记录缺轮次、调用无返回）时，卡片仍显示调用本身，并标明缺失，不猜测归属。
- 卡片标题使用 Context Agent 派发时写的一句任务说明（作者已确认）。派发工具只接受产物编号，Sub 收到的是 Writing Brief、Context Pack、初稿等材料原文，无法直接当标题；因此派发 Sub 的工具契约增加一个必填的简短任务说明参数：
  - 这句说明只保存到该次执行的记录中、显示给作者，**不进入 Sub 的输入**，因此不改变 Writing Agent 不接收自由文本、不接收作者对话的边界（ADR 0001、0005）。
  - 说明为空或过长时，工具拒绝并提示 Context Agent 重写，长度上限是参数细节，可在实现时确定。
  - Context Agent 的系统提示补一条：派发时用作者能读懂的话写这次要做什么，不复述材料。
  - 已有的旧执行记录没有说明时，标题显示 Sub 身份，并注明"未写任务说明"，不从材料中猜测。
- 追加要求卡片的正文取自 Context Agent 给 Writer 发消息时的消息原文。

### 3. 任务视图契约的扩展

在现有任务视图上增加过程信息，原有字段保留，供 CLI 与旧页面逻辑兼容。以下为类型形状，字段名可调整：

```ts
type ProcessItem =
  | { kind: "message"; id: string; role: "user" | "assistant"; text: string; at: number }
  | { kind: "thinking"; id: string; text?: string; unreadable?: boolean; at: number }
  | { kind: "tool"; id: string; name: string; args: unknown; output?: string; result?: string;
      error?: boolean; state: "running" | "done" | "error" | "stopped" | "interrupted"; at: number }
  | { kind: "event"; id: string; event: string; text: string; at: number }
  | { kind: "unknown"; id: string; type: string; raw?: string; at: number };

type RunOutcome = "running" | "stopping" | "returned" | "replied" | "no-result"
                | "failed" | "stopped" | "interrupted";

interface SubRunView {
  agentId: string; round: number; dispatchCallId?: string; continued: boolean;
  title?: string;                 // Context Agent 派发时写的任务说明；追加要求为消息原文
  instruction: string;            // 派发要求或追加要求原文（详情面板与原始调用使用）
  outcome: RunOutcome; startedAt: string; endedAt?: string;
  results: Array<{ draftId?: string; artifactId: string; title: string; summary: string; readable: boolean; finalized?: boolean }>;
  lastMessage?: string; error?: string; liveAction?: string;
  items: ProcessItem[];           // 该次执行的过程
}
```

- 任务视图带上 Context Agent 的过程项（按时间）和每个 Sub 的每次执行。每次执行的成果直接由该执行记录的成果列表生成，说明行复用现有的检查结论文字。
- 结果判定集中在服务端一处：
  - 进行中，作者已请求停止时为正在停止；
  - 结束且保存了成果为已交回；
  - 没有成果但有最后一句话为已回复；
  - 两者都没有为未交回成果；
  - 失败、停止、中断照实。
  
  执行结果为"retired"的，按其说明归入已停止，不新增状态词。
- 页面仍通过现有的状态轮询获取完整视图，本规格不引入推送通道。过程很长时允许按任务分段返回，但同一消息或调用在多次读取之间的身份保持稳定，页面据此合并。

### 4. 页面展示（纯推导 + 渲染）

- 页面拿到任务视图后，先由一个纯推导层把它转成展示模型，再渲染。纯推导层不访问 DOM，也不访问网络：
  - 按作者消息切分轮次；
  - 判定每轮是否进行中、是否异常结束，并生成"已处理 X 秒／X 分 Y 秒"和"处理 X 秒后失败"等收起行；
  - 把相邻的思考与工具合成一组，生成"动作 + 对象"摘要；
  - 生成子任务卡片、子任务入口文案、列表排序和面板内容顺序。
- 动作摘要的映射只依据工具名和参数，不依据 Agent 角色。以下是原型确定的规则，可以直接沿用：
  - 读取、编辑、写入按文件名归并，如"读取了 chapter-1.md"；
  - 搜索、命令单独成句；
  - 已知的 Noya 工具使用固定短语："查阅设定"带对象名；"提交正文《标题》"；"保存方案""保存检查""应用资料变更""派出子任务""追加要求"；
  - 未知工具显示原名；
  - 进行中的写成"正在…"并排在最后，断线时加"最后已知 · "；
  - 失败、停止、未完成的写成"修改 x 失败／已停止／未完成"并排在最前；
  - 返回内容为"No changes applied"的写成"未改动 x"；
  - 超过 3 项时显示前两项加"等 N 项"。
- 常规的执行开始、正常结束、停止请求，以及 Context Agent 自身的错误和中断事件，不在过程里单独成行。它们由收起行、卡片和页面提示表达。
- 收起与展开状态、打开的面板、阅读位置以"作品 + 任务"为边界保存在本机。这沿用现有的按任务保存输入与阅读位置的做法，刷新后恢复。
- 右侧只有一个槽位，由详情面板或成果阅读器占用。成果阅读器记录它是从面板打开还是从信息流打开，用来决定底部按钮显示"返回子任务"还是"返回"。
- 子任务入口的文案优先级：
  1. 仍在屏幕上的进行中卡片优先，入口只显示计数；
  2. 只有一个进行中，显示它的当前动作；
  3. 多个进行中，显示数量；
  4. 有失败时追加失败数，或单独显示失败数；
  5. 都结束后显示总数。
- 发送与停止共用一个按钮位置：本任务执行中且输入为空时显示停止，否则显示发送。停止命令始终带实际执行任务的身份。
- 无障碍：
  - 卡片头部、收起行和原始调用开关都是可聚焦按钮，并带展开状态；
  - 面板关闭后焦点回到对应卡片；
  - 窄屏全屏时焦点限制在面板内。

### 5. 提意见与定稿

- "对这版提意见"沿用现有发消息时引用稿件编号的能力，并在输入框上方显示引用对象和版本。
- "将这版定稿"沿用现有定稿命令和内容指纹校验；执行中拒绝。定稿后，所有出现这份成果的位置都从同一份稿件视图读取"作者已定稿"。

### 6. Context Agent 的收尾回复

- 作者已确认：一轮里的子任务都结束、Context Agent 不再等待后台通知时，它用一条回复说明本轮结果和需要作者决定的事。这一条就是收起后保留的"最后一条回复"。
- 只在 Context Agent 的系统提示里加这条要求，不在代码中强制或代写这条回复。仍在等待后台通知时照旧简短告知正在进行。

## Testing Decisions

- 好的测试只验证外部行为：给定一段真实的 Agent 执行过程（由测试替身模型产生），作者在任务视图或页面上看到什么、能做什么。测试不断言内部数据结构、私有方法或 CSS 类名。
- **主测试接口：本机应用的任务视图与命令。**沿用现有本机应用测试和写作任务测试的做法：用测试替身模型为 Context Agent、Writer、检查员设定响应，通过发命令驱动执行，再读取任务视图并断言。覆盖：
  - Context Agent 的工具调用、思考与消息按顺序出现在过程中，原工具名、参数与返回完整；
  - 派发、追加要求与 Sub 执行记录一一对应，每次执行只挂自己的成果，检查成果带结论；
  - 已交回、已回复、未交回成果、失败、已停止、已中断的判定；
  - 停止后无返回的调用标为"未收到最终返回"，重启后进行中执行变为中断，已结束的结论保留；
  - 任务 A 运行时读取任务 B，B 的视图不含 A 的过程；
  - 多次读取同一任务时，消息与调用身份稳定、无重复；
  - 旧任务会话缺失或单份成果损坏时，视图仍返回其余内容并标出缺失。
- **次测试接口：页面的纯推导层。**它不依赖浏览器，用 node 内置测试直接喂入任务视图样例。覆盖：
  - 轮次切分与收起行文字（秒、分秒、失败、中断、停止）；
  - 动作摘要的全部规则；
  - 子任务入口文案优先级与列表排序；
  - 面板内要求、执行、追加要求的时间顺序。
  
  原型中的固定样例可以改写成这里的测试数据。
- **验收证据：浏览器走查。**沿用写作任务那一轮的做法，用脚本在真实本机服务上走一遍，保存截图与文字输出到本功能的 `evidence/` 目录。覆盖：
  - 桌面与窄屏的运行中、收起、列表、面板、成果返回；
  - 断线与停止。
  
  它不替代上面两层测试。
- 先例：本机应用测试、写作任务测试和记录读取测试（测试替身模型 + 本机应用 + 断言视图），以及写作任务一轮的浏览器检查脚本。

## Out of Scope

- 使用统计和埋点。
- 新的推送通道（如服务器推送事件或 WebSocket），继续使用现有轮询。
- 作者直接给 Sub 发消息；输入始终发给 Context Agent。
- 在信息流内编辑成果正文；成果只读，修改通过对话完成。
- 按业务角色定制过程展示，例如给检查员单独的报告样式。成果条目的一句说明除外。
- 改变 Sub 的调度、派发参数或执行策略本身。
- 对没有保存过程的历史任务补写过程。
