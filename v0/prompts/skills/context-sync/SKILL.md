# Context 同步

## 收到通知时

| 通知 | 下一步 |
|---|---|
| "某章已定稿，请进行 Context 同步" | 第 1 步 |
| 核对员完成，提交了 `check_N` | 第 4 步 |
| 核对员失败或被停止 | 同一份清单重新派一次；仍失败就告诉作者 |

## 1. 读

用 `query_canon` 取定稿正文（`get` 章节 ID），以及正文涉及的人物、地点、组织、物品、功法、大纲节点的现有资料。

## 2. 列变化

只列正文实际带来的变化。每条附定稿正文中逐字复制的连续摘录（`evidence`，不改字、不拼接）和一句理由（`rationale`）。

要列的：

- 人物：状态、位置、持有物、能力、资源、关系、认知的变化。
- 新出现、之后会反复使用的地点、组织、规则、功法、物品。
- 大纲：相关节点的状态（`written` / `in_progress`）与 `chapter_ids`。
- 必需一条 `chapter_meta`：本章摘要（按正文实际发生的事概括）与重要登场角色（参与关键行动、对话或有重要状态变化的人物）。

不列的：

- 只被提及的人物；
- 正文没有确认的推测、传闻或人物的打算；
- 作者对未来的计划，除非作者在对话中明确要求写进大纲。

修改已有对象时，`upsert` 是整份替换：先取出当前完整内容，只改正文带来的部分，其余原样保留。

## 3. 提交与核对

`save_sync_proposal` → `spawn_subagent({ role: "sync_checker", proposal_id })` → 结束本轮等通知 → 读取核对结果。

只有清单改正后重新提交时才再派核对员；不为得到更好的结论重复核对同一份清单。

## 4. 按结论处理

- `supported`：纳入。
- `unsupported`：删掉；若是清单本身写错了（摘录选错、多写了内容），改正后作为新清单提交并核对。
- `conflict`：向作者说明冲突双方（正文怎么写、既有资料怎么写），请作者决定写入还是不写。作者要改写内容时，改正后作为新清单提交并核对。

需要作者决定的变化，一次列清楚、一次问完。

## 5. 应用

`apply_sync` 选入要写入的变化，`chapter_meta` 必须在其中。包含非 `supported` 的变化时，`author_confirmation` 填作者同意时的原话片段，逐字复制。

从结果确认该章已移出待同步。简短告诉作者更新了哪些资料、交由作者决定的几处结果如何。如果作者之前要写下一章，现在回到 `write-chapter`。
